Tokenization

Tokenization and byte-pair encoding

The model never sees text. It sees integers, and the tokenizer is the fixed, separately trained program that converts between the two. Its design choices leak into everything downstream: how long sequences are, what the model finds easy or hard, what a request costs, and even which languages are served well. This module builds the algorithm GPT-2 uses (byte-level BPE) from scratch and examines its consequences.

Code companion: notebooks/02_tokenization_bpe.ipynb implements BPE in about 50 lines, trains it on Shakespeare, and proves it matches OpenAI's GPT-2 and GPT-4 tokenizers exactly. Open in Colab · View on GitHub

1. Why not characters or words?

The model needs a fixed vocabulary of V symbols, each with its own learned embedding row. The choice of symbol sets a tradeoff:

UnitVocabularySequence lengthProblem
Characters / bytestiny (256 bytes)very long (≈ 5× words)attention cost grows with length squared; each step carries little meaning
Wordshuge, open-endedshortlong tail of rare forms; anything unseen becomes <unk>
Subwords (BPE)tens of thousandsin betweennone of the above, at the price of odd splits

On Shakespeare (the notebook measures this) there are 25,670 distinct whitespace-separated word forms in 202,651 words, and 14,919 of those forms occur exactly once. A word-level vocabulary would be mostly rare forms the model sees once. Subword units fix this: frequent words are single tokens, rare words are built from reusable pieces.

2. Byte-pair encoding

BPE began as a data-compression trick (Gage, 1994). Sennrich et al. (2016) applied it to neural machine translation to handle rare words, and it has been the basis of GPT-style tokenizers since. The idea is simple.

Training the tokenizer

  1. Start with a vocabulary of single symbols (characters, or bytes).
  2. Count every adjacent pair of symbols in the training text.
  3. Merge the most frequent pair into a new symbol and add it to the vocabulary.
  4. Repeat until the vocabulary reaches the target size.

The output is an ordered list of merges. Figure 2 replays the toy example from the paper: low appears 5 times, lower 2, newest 6 and widest 3, with an end-of-word marker </w>.

Merged pieces are added, not substituted. The two symbols that were merged stay in the vocabulary. In Figure 2 the first merge makes es (from e + s); a later merge joins es + t into est. Both are separate entries, and est could only be learned after es existed. The vocabulary size is therefore the starting alphabet plus the number of merges. Once est exists, es is used less (it still appears in words like buses), and a few early merges end up almost unused.

Frequent fragments such as est</w> become single units that newest and widest share, while lower keeps low plus leftover letters. Run on real text, the same procedure first learns common letter pairs, then whole words, then rarer fragments (Figure 3).

Encoding new text

To tokenize a new string, split it into the same kind of pieces and, inside each piece, repeatedly apply the learned merge that was learned earliest until none applies. Decoding is concatenation: each token id maps to a byte string, and the bytes are joined and read as UTF-8. The whole tokenizer is therefore just a dictionary from byte strings to ids; the notebook's encoder needs nothing else, which is why the same few lines run both our Shakespeare vocabulary and OpenAI's.

3. Byte-level BPE and pre-tokenization (GPT-2)

Two refinements turn BPE into the tokenizer GPT-2 uses (Radford et al. 2019, section 2.2).

Bytes as the base alphabet. Instead of Unicode characters, the starting symbols are the 256 possible byte values of the UTF-8 encoding. Any string in any script, any emoji, even invalid text can be written as bytes, so nothing is ever out of vocabulary. GPT-2's vocabulary is exactly 256 bytes + 50,000 merges + 1 special token (<|endoftext|>) = 50,257.

What the 256 base tokens are. Each is one byte value, 0 to 255, and none of them is learned from the corpus. Converting text to bytes is the fixed UTF-8 standard: English letters, digits and common punctuation take one byte each, accented letters two, most CJK characters three, emoji four (Figure 4). The base tokens exist even for byte values that never occur in your data. The corpus only decides the merges, that is, tokens 256 and up, and the order they were learned in. This is different from character-level BPE, where the starting alphabet is whichever characters the corpus contains, so unseen characters need an unknown token.

Token ids are arbitrary labels. Which id a byte gets is a choice by the tokenizer's designers. A simple tokenizer would use id = byte value, and the notebook's does. GPT-2 does not: its table puts the printable characters first, so ! is id 0, A is 32 (byte 65), a space is 220, and byte 0 is 188; cl100k_base uses the same numbering for these. It does not matter, because an id is only an index into the embedding table, whose rows start random and are learned. Merged tokens are numbered in the order their merges were learned.

Decoding runs the pipeline backwards: ids become byte strings, the bytes are concatenated, and the result is read as UTF-8. If generation stops partway through a multi-byte character (say two of the three bytes of 世), the bytes are not valid UTF-8 yet, so streaming decoders wait for more tokens or show the replacement character �.

Pre-tokenization. Before any merging, a regular expression splits the text into pieces, and merges happen only inside a piece. Without this, BPE would learn tokens like dog. and dog! as separate things, wasting vocabulary. GPT-2's pattern separates contractions, runs of letters, runs of digits, runs of punctuation and whitespace; a leading space stays attached to the word that follows it, which is why  hello and hello are different tokens.

GPT-4's tokenizer (cl100k_base, 100,277 entries) keeps the algorithm and changes the regex: contractions match case-insensitively, a single leading punctuation mark can attach to a word, and digit runs are split into groups of at most three. GPT-4o's o200k_base has about 200,000 entries and better multilingual coverage. All three are in the tiktoken library, and the notebook checks our encoder against each of them.

4. How big should the vocabulary be?

Each merge shortens sequences on average, but with diminishing returns: the first merges join very common pairs, later ones join rare ones. Figure 6 trains our BPE on Shakespeare and measures the compression on held-out text.

A bigger vocabulary shortens sequences (cheaper attention, more text per context window), but it grows the embedding matrix and the output layer (V×d parameters each; 38.6M of GPT-2's 124M parameters are the embedding), and the rare tokens at the end of the list get few training examples. Practical vocabularies have grown from 50k (GPT-2) to 100k (GPT-4) to 200k (GPT-4o) as models and training sets grew.

5. Other tokenizers

  • WordPiece (used by BERT; described in Wu et al. 2016) also builds a vocabulary bottom-up, but chooses merges that most increase the likelihood of a language model over the training data rather than the raw pair frequency. It marks word-internal pieces with ## and has an [UNK] token for what it cannot represent.
  • Unigram language model (Kudo 2018) works top-down: start with a large candidate vocabulary and prune the tokens whose removal hurts likelihood least. Because a string can have several segmentations, it supports sampling them during training as a regulariser.
  • SentencePiece (Kudo & Richardson 2018) is a library that implements BPE and unigram directly on raw text, treating whitespace as an ordinary symbol (▁), so it needs no language-specific pre-splitting. Many open models (Llama 2, T5) use it.

6. What tokenization does to the model

Spelling, case, spaces and numbers

The model sees token ids, not letters, so tasks defined on letters are indirect for it: counting the r's in strawberry requires knowing the spelling of tokens it has only seen as units. Surface changes can change the tokens completely: hello,  hello and HELLO are unrelated ids, and numbers are cut into arbitrary chunks that differ between tokenizers, which makes digit-level arithmetic harder than it looks.

Some languages cost more

BPE vocabularies reflect the data they were trained on, which is dominated by English. Text in other languages is split into smaller pieces, so the same sentence needs more tokens, which means a shorter effective context window, slower generation and a higher bill (Petrov et al. 2023; Ahia et al. 2023). Figure 8 measures one sentence in five languages across three real tokenizers. Newer vocabularies narrow the gap considerably.

Glitch tokens

The tokenizer is trained separately from the model, on possibly different data. A string frequent enough to earn a token in the tokenizer's data may be almost absent from the model's training data. Such tokens have embeddings that were barely updated and can trigger strange behaviour; Land & Bartolo (2024) describe methods for automatically detecting these under-trained tokens.

7. Common misconceptions

  • "Tokens are words." They are frequency-driven fragments that often coincide with words but need not.
  • "The tokenizer is learned along with the model." It is trained once, beforehand, by counting; the model's weights are trained afterwards with the vocabulary frozen.
  • "Byte-level BPE has to see every character during training." No: any unseen character is simply written as its bytes.
  • "More tokens per text means a worse model." It means a different cost, not a lower quality; but it shortens the effective context and raises latency.
